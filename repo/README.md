# School Result Processing and GPA Engine

**Team ID** LSH26-T013 · **Problem ID** P08 · **Repository** `lsh26-t013-p08`

**Live URL** _(paste after deploying)_

A result office tool for a school running the Bangladeshi GPA scheme. Marks go in, the engine
applies rules R-10 to R-13, and the office gets a result sheet, a per-student calculation trace
that names the rule behind every grade point, and three checking lists to verify by hand before
results go out.

---

## Setup and run

No dependencies to install.

```bash
git clone https://github.com/<org>/lsh26-t013-p08
cd lsh26-t013-p08
npm test          # 52 engine assertions, including all 11 hard-edge cases
node dev-server.js   # http://localhost:3000
```

Deploying to Vercel: import the repository, accept the defaults, deploy. `vercel.json` points
the static build at `public/` and Vercel picks up `api/*.js` as serverless functions
automatically. There is no build step and no environment variable to set.

### Signing in

The first screen is the login portal. Demo accounts are listed on the login card itself and
fill the form when tapped, so no credentials need to be typed during judging.

| Role | Username | Password | Lands on |
|---|---|---|---|
| Operations | `ops.admin` | `ops1234` | Dashboard, all four required items |
| Executive | `exec.head` | `exec1234` | Dashboard, read-only |
| Teacher | `teacher.shirin` | `teach1234` | All results and traces, read-only |
| Teacher | `teacher.mahbub` | `teach1234` | All results and traces, read-only |
| Student | `student.s001` | `stud1234` | Own result — the strong-average failure |
| Student | `student.s008` | `stud1234` | Own result — GPA 5.00 |
| Guardian | `guardian.s001` | `guard1234` | Two linked children |

A teacher's own subjects are scoped to their assignments, and teachers additionally have
read-only access to every student's result and trace. Students see only their own result;
guardians see only the students linked to their account.

Sessions are stateless HMAC-SHA256 signed tokens (`lib/auth.js`), because serverless
instances share no memory. Passwords are stored as SHA-256 hashes, never in plain text.
Every API route calls `requireRole()` before touching data: a student token gets 403 on the
office routes and 403 on another student's result, and an edited token gets 401. The
navigation is role-aware, but the navigation is not the control.

### Sample data and reset

The dataset is a bundled fixture in `lib/seed.js`, generated by a fixed-seed PRNG, so every
run produces the same 62 students. "Restore sample data" on the dashboard calls `/api/reset`
and rebuilds it. Nothing to upload, nothing to configure.

## Major decisions

**Node serverless instead of PHP and MySQL.** The original brief specified PHP with MySQL.
Vercel has no PHP runtime and no MySQL server, so hosting on Vercel and using PHP are mutually
exclusive. Hosting was the binding constraint, so the backend is Node serverless functions.
The frontend is still plain HTML, CSS and vanilla JavaScript with no framework, as specified.

**No stored GPA anywhere.** Results are computed by the engine on every read rather than
written to a results table. A rule fix or a revised mark can never leave a stale grade behind,
and the trace can never disagree with the result sheet.

**One grading policy file.** `lib/grading.js` holds every pass mark, every grade-point band,
every letter boundary and the GPA constants. No other file contains a threshold. Changing the
grading scheme is a one-file edit.

**Rule IDs travel with the result.** `evaluateSubject` returns `ruleId` and `ruleText`
alongside the grade point, so the trace renders what the engine actually decided instead of
re-deriving an explanation in the template.

**Rule order: absence before low marks.** A student who is absent and would also have failed
on marks reports R-12, because absence is the more specific fact about that row.

## Documented assumptions

The problem statement fixes the pass marks and the GPA formula but never gives the mark to
grade-point table. Three gaps were filled and are configurable in `lib/grading.js`:

1. **Grade-point bands** follow the standard 80 / 70 / 60 / 50 / 40 / 33 scheme, consistent
   with the 25 + 8 = 33 pass total implied by the stated pass marks.
2. **Theory-only subjects** are marked out of 100 with a pass mark of 33. Keeping them at 75
   would cap every theory-only subject at grade point 4.00.
3. **Rounding** is half-up to two decimals, and the letter band is applied after rounding.

The letter grade list in the brief runs `A-` and `B` together in one line; it is read as
A- = 3.50–3.99 and B = 3.00–3.49.

## Known limitations

- Data lives in memory per serverless instance. Reads are consistent because the fixture is
  deterministic, but writes would not persist across instances — mark entry and the challenge
  workflow are not yet wired to a database.
- Mark entry, the rechecking challenge workflow, the audit log and notifications are
  specified in `docs/PLAN.md` but not implemented in this commit. Role-based panels,
  authentication, server-side role guards and result publication are implemented.
- PDF export is not implemented. CSV export works on the results and checking-list pages.
